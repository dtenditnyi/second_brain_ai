## Часть 0. Общее для всех раундов

Запуск и тесты — `start.bat` (`start.ps1`), команды — в `CLAUDE.md`. История — `docs/audit/REPORT.md`, `DECISIONS.md`, `LOG.md`, `STATUS.md`, `docs/BUGS.md`.

Хранилище владельца — Obsidian «Danylo», GitHub `Lol4ik0/myObsidian`, синхронизация на ПК/ноутбуке/телефоне через obsidian-git. Структура PARA:

Правила заметок: frontmatter `tags` (1–3, только из списка), `type`, `status` (active/paused/completed/idea), `date`, `aliases`. Плагины владельца: Dataview, Templater, Calendar, Iconize, obsidian-git.

### 0.2 Ветки
1. Проверь, что `feature/audit` уже в `main` (`git merge-base --is-ancestor origin/feature/audit origin/main`). Если нет — слей её в `main` с `--no-ff` и запушь (владелец это одобрил). Это единственное слияние в `main` за всё задание.
2. Round 3 — ветка `feature/round3` от свежего `main`.
3. Round 4 — ветка `feature/round4` от завершённой `feature/round3`.
4. Round 5 — ветка `feature/round5` от завершённой `feature/round4`.

### 0.3 Правила безопасности (нарушать нельзя)
- Прод-БД (Postgres) и `ai_manager/db.sqlite3` не трогать; локально — только `audit_copy_db.sqlite3` и in-memory тестовые БД. Существующие docker-контейнеры и volumes не трогать.
- `.env` не читать, не выводить и не коммитить.
- Внешние API (Gemini, Ollama, Anthropic, GitHub, HuggingFace, Telegram) в тестах — только моки.
- Настоящий репозиторий хранилища на GitHub не трогать — только локальные тестовые git-репозитории во временных папках (bare «удалённый» + несколько клонов). Для тестов рендера — фикстура-хранилище, повторяющая структуру и стиль владельца (вымышленные заметки).
- Историю git не переписывать, force push запрещён.

### 0.4 Автономность
Работай полностью автономно, **вопросов владельцу не задавай и подтверждений не жди**. Спорные решения принимай сам и записывай в `docs/audit/DECISIONS.md`. Если что-то невозможно проверить в этом окружении (например, нет Docker) — сделай максимум доступных проверок, честно запиши ограничение в LOG и REPORT и продолжай. Единственное, что запрещено делать без владельца, — действия против правил 0.3.

### 0.5 Методика (для каждого раунда N = 3, 4, 5)
1. Прочитай `CLAUDE.md`, `README.md`, `docs/audit/REPORT.md`, `DECISIONS.md`, `STATUS.md`, `LOG.md`, документацию из предыдущих раундов и код затронутых модулей.
2. Создай `docs/audit/roundN/GOALS.md`: нумерованные цели из раздела этого раунда; у каждой — проверяемые критерии приёмки и id тестов, которые их проверяют.
3. **Acceptance-тесты до кода:** `tests/acceptance/test_roundN.py` (+ e2e/responsive-части) — минимум один тест на каждый критерий. Каждый ещё не выполненный тест помечай `@pytest.mark.xfail(strict=True, reason="RN Gx")`: прогоны остаются зелёными, а случайно «прошедший» тест сломает сборку. Первый прогон (все xfail) → `docs/audit/roundN/acceptance-start.txt`. Отдельный коммит «test(rN): acceptance tests for Round N goals».
4. Реализация маленькими шагами. **После каждого изменения** — быстрые тесты: `../venv/Scripts/python.exe -m pytest -m "not e2e and not responsive" -q` (из `ai_manager/`). После каждой цели — снять `xfail` с её тестов, убедиться, что они зелёные. После каждой части — полный прогон `start.bat -FullTests -NoServer`. Коммитить только при зелёных тестах. На каждый новый модуль — unit-тесты, на каждый багфикс — регрессионный тест. Если доступен `pytest-cov` — покрытие новых модулей ≥ 90 %.
5. **Запрещено** ослаблять, удалять или пропускать acceptance-тесты ради прохождения. Менять тест можно только если цель была понята неверно — с записью в DECISIONS, почему.
6. **Не переходи к следующему раунду, пока:** все цели раунда выполнены; в `tests/acceptance/test_roundN.py` нет ни одного `xfail`; полный прогон зелёный; независимая проверка пройдена.
7. **Независимая проверка** отдельным агентом со свежим контекстом: сверяет GOALS с кодом и тестами, делает мутационные проверки (намеренно ломает ключевую логику — тесты должны упасть), ищет баги и уязвимости. Отчёт агента → `docs/audit/roundN/VERIFY-1.md` (и `VERIFY-2.md` при втором круге). Все находки исправить с регрессионными тестами и перепроверить; до 2 кругов.
8. Финал раунда: полный прогон → `docs/audit/roundN/test-run.txt`; раздел «Round N» в `docs/audit/REPORT.md` (что сделано, что не проверено вживую, точные действия для владельца); обновить `CLAUDE.md`, README, `.env.example`, `docs/DEPLOY.md` при изменениях; `STATUS.md`: «Round N = DONE»; пуш ветки; сразу начать следующий раунд.

### 0.6 Журналирование (обязательно, как в прошлых раундах)
- **`docs/audit/LOG.md`** — хронологический журнал. Запись после каждого значимого шага (каждое изменение кода + прогон тестов, каждая цель, каждый коммит, каждая проверка агентом). Формат записи:
  `### YYYY-MM-DD HH:MM — Round N / Gx — краткий заголовок`
  - Что сделано и зачем (1–3 строки)
  - Файлы: список изменённых/созданных
  - Команды/проверки: какие тесты запускались и результат (passed / failed / xfail — числа)
  - Коммит: хэш и сообщение (если был)
  - Проблемы/отклонения от плана (если были)
- **`docs/audit/DECISIONS.md`** — каждое принятое самостоятельно решение: номер, вопрос → решение → почему → где в коде.
- **`docs/BUGS.md`** — каждый найденный баг (новый номер B-xx): симптом, причина, исправление, регрессионный тест, статус.
- **`docs/audit/STATUS.md`** — обновлять после каждой цели: текущий раунд и цель, что сделано, что осталось, «Следующий шаг: …» (чтобы прерванную работу можно было продолжить ровно с этого места).
- **`docs/audit/roundN/`** — GOALS.md, acceptance-start.txt, test-run.txt, VERIFY-*.md, скриншоты responsive.
- Каждый запуск `start.bat` уже пишет лог в `logs/runs/` и `history.csv` — в LOG.md ссылайся на имя файла запуска.
- Коммиты — маленькие, с понятными сообщениями (`feat(...)`, `fix(...)`, `test(...)`, `docs(...)`), с номерами целей/багов.
- В самом конце всего задания — **`docs/audit/SUMMARY_ROUNDS_3-5_RU.md`** на русском, коротко для владельца: что сделано в каждом раунде, сколько тестов, что не проверено вживую, что ему сделать руками (слить ветки, деплой на сервер, перенос задач, токены, Cloudflare Access), и порядок действий.

## Round 3 — Markdown в чате, доработки UI, задачи в заметке Obsidian, подготовка к домашнему серверу

Порядок частей: A → C → B.

### Часть A — доработки
A1. **Markdown в ответах ИИ** (чат и Status Report): заголовки, списки, жирный/курсив, ссылки, таблицы, блоки кода с подсветкой и кнопкой «Копировать», inline-код, цитаты, чекбоксы, callouts `> [!info]` и т.п. Библиотеки — локально в `static/` (без CDN). Обязательная санитизация (DOMPurify или серверный аналог); все XSS-тесты прошлых раундов зелёные + новые (`<script>`, `onerror`, `javascript:`, SVG внутри Markdown). Ссылки `rel="noopener noreferrer" target="_blank"`. `[[Вики-ссылки]]` в ответе ведут на страницу заметки. Таблицы и код не ломают вёрстку на 320 px. История и новые ответы рендерятся одинаково.
A2. **Core Matrix на планшетах:** на 768–1279 px без горизонтального скролла (карточки или скрытие второстепенных колонок с раскрытием строки); ≥1280 — таблица. Responsive-тест: нет переполнения на всех 11 размерах (320, 375, 390, 414, 667×375, 768, 834, 1024, 1280, 1440, 1920).
A3. **Core Matrix следует теме** (светлая/тёмная, акцент) через общую дизайн-систему, сохраняя «консольный» характер; контраст WCAG AA в обеих темах.
A4. **Логи вне git:** `git rm --cached` для отслеживаемых логов, `.gitignore`, `logs/.gitkeep`; приложение само создаёт папку логов; ротация логов Django/RAG по размеру и количеству.

### Часть C — задачи живут в одной заметке Obsidian (единственный источник правды)
Цель: все задачи сайта хранятся в одной заметке хранилища. Сайт читает их оттуда и записывает изменения обратно (commit + push); правки из Obsidian на ПК/телефоне и из Telegram-бота (через API в Round 4) появляются на сайте.

C1. **Формат** — описать в `docs/TASKS_FORMAT.md` (контракт и для бота):
- Путь настраивается (`TASKS_NOTE_PATH` + поле в Настройках), по умолчанию `01 - Projects/🎯 Цели и планы/Задачи.md`; если заметки нет — сайт создаёт её с frontmatter `tags: [planning]`, `type: tasks-db`, `status: active`, `date`, `aliases: [Задачи, Tasks]` и строкой `🔗 [[Главная (Home)]]` внизу.
- Одна задача = одна строка-чекбокс, совместимая с Dataview и плагином Tasks: `- [ ] Сдать лабу по физике 📅 2026-11-14 ⏫ #university ➕ 2026-11-11 🆔 t7k2m9`. Статусы `[ ]` todo, `[/]` in progress, `[x]` done (+ `✅ дата`), `[-]` отменено. Приоритеты `⏫` / `🔼` / `🔽`. Теги — только из разрешённого списка. Стабильный короткий уникальный `🆔`; строкам без ID сайт добавляет ID при следующей записи.
- Разделы по заголовкам (например `## 📥 Входящие`, `## 🔥 Срочно`, `## ✅ Выполнено`) — на твоё усмотрение (DECISIONS); статус определяется символом чекбокса, а не разделом. Новые задачи по умолчанию — в «📥 Входящие».
- Всё, что не является задачей (текст, Dataview-блоки), сохраняется байт в байт; неизвестные поля в строке задачи не теряются.

C2. **Парсер/сериализатор** — чистый модуль без Django (`core/tasks_md.py` или пакет), пригодный для переиспользования в боте. Тесты: parse → serialize даёт исходный текст; кириллица, эмодзи, CRLF/LF, пробелы, вложенные подзадачи, строки без ID, дубликаты ID (property-based, если доступен hypothesis).

C3. **Единый механизм записи в хранилище** (`core/vault_writer.py` или аналог) — им пользуются все последующие части (редактор, ИИ-агент, API): блокировка между воркерами gunicorn (advisory lock Postgres / файловый lock) → `pull` → применить операцию → commit (понятное сообщение, автор «Second Brain») → `push`; если push отклонён — заново `pull` и повторно применить ту же **операцию** (а не перезаписать файл), до N попыток. Валидация путей (только внутри хранилища, не `.git/`, не `.obsidian/`, защита от `../`, симлинков, абсолютных путей). Для задач — операции по ID: добавить / изменить текст / статус / срок / приоритет / теги / удалить. Если задачу удалили в другом месте — понятное сообщение без падения. Если у PAT нет права записи — понятная ошибка в UI и в Настройках (нужно Contents: Read and write).

C4. **Чтение и актуальность:** модель `Task` — кэш/индекс заметки, а не источник правды. Обновление при открытии страниц задач/главной, если прошло больше `TASKS_SYNC_INTERVAL` (60 с), кнопка «Обновить», management-команда `sync_tasks` (для периодического запуска в проде); в UI — время последней синхронизации и ошибки.

C5. **Офлайн:** если GitHub недоступен — операция в очередь (outbox в БД), задача сразу видна с пометкой «не синхронизировано»; очередь отправляется при следующей успешной синхронизации в исходном порядке.

C6. **Перенос старых задач:** команда `export_tasks_to_note` с `--dry-run` (показывает итоговую заметку) и реальным режимом; повторный запуск не создаёт дублей. На прод-БД не запускать — описать в REPORT/DEPLOY.

C7. **UI:** сохранить всё, что есть (статусы To Do / In Progress / Done), добавить срок, приоритет, теги, удаление с подтверждением; у каждого пользователя своя заметка задач в своём хранилище. Красиво и удобно на телефоне и ПК.

C8. **Тесты:** реальные локальные git-репо — два клона одновременно пушат изменения (повтор без потерь), заметка с посторонним текстом не портится, outbox, нет прав записи, многопользовательская изоляция; e2e и responsive.

### Часть B — прод на домашнем сервере (Proxmox → VM Ubuntu Server 24.04 LTS, работа 24/7)
Сервер недоступен: подготовь всё в репозитории и проверь локально. Цель: на чистой Ubuntu владелец клонирует репо, заполняет `.env`, запускает один скрипт — сайт работает постоянно, сам поднимается после перезагрузки и падений, обновляется одной командой, бэкапится каждый день.

B1. **Прод-конфигурация** (`Dockerfile`, `docker-compose.yml`, `settings.py`, `requirements.txt`):
- Tailwind `npm run dev` в проде не запускается; CSS собирается при сборке образа.
- Dockerfile multi-stage (CSS собирается в node-стадии, в финальном образе нет node/gcc), не-root пользователь, `PYTHONDONTWRITEBYTECODE`/`PYTHONUNBUFFERED`, `git` в образе; `.dockerignore` (venv, node_modules, *.sqlite3, logs, .env, .git, chroma_db, obsidian_data, docs/audit/responsive, cloudflared.exe).
- entrypoint: ждать Postgres → `migrate --noinput` → `collectstatic --noinput` → gunicorn (воркеры/таймаут из env; по умолчанию 2 воркера, `--timeout 300`).
- Периодический `sync_tasks` (отдельный лёгкий сервис-планировщик или systemd timer).
- `restart: unless-stopped` у всех сервисов; healthcheck web (новый `/healthz/` без авторизации и без ИИ, проверяет БД) и Postgres (`pg_isready`); `depends_on: condition: service_healthy`.
- Постоянные volumes: Postgres, `chroma_db`, `obsidian_data`, кэш HuggingFace, логи, `staticfiles`.
- Postgres и web наружу не публиковать — только через cloudflared (токен из `.env`); опционально порт web на `127.0.0.1`/LAN через переменную.
- Ротация docker-логов, часовой пояс `Europe/Bucharest`.
- Django-прод: ошибка при старте, если `SECRET_KEY` пустой или дефолтный при `DEBUG=False`; `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` из env (текущие значения по умолчанию); secure-cookies, HSTS, `SECURE_PROXY_SSL_HEADER`; `manage.py check --deploy` без критичных предупреждений.
- `OLLAMA_HOST` — Ollama на другом ПК в домашней сети (пример `http://<IP-ПК>:11434`); Auto-Hybrid корректно переходит на Gemini, если ПК выключен (тест).
- `.env.example` — все переменные (без секретов), включая `TASKS_NOTE_PATH`, `TASKS_SYNC_INTERVAL`.

B2. **Скрипты `deploy/`** (bash, `set -euo pipefail`, понятный вывод, логи):
- `install.sh` — чистая Ubuntu 24.04: Docker Engine + compose plugin из официального репо Docker, пользователь в группе docker, проверка `.env` (обязательные переменные заданы, значения не выводить), сборка, запуск, ожидание healthcheck, итог. Идемпотентный.
- `update.sh` — `git pull` → бэкап → пересборка → миграции → перезапуск → `/healthz/`; при провале — откат на предыдущий образ/коммит.
- `backup.sh` — сжатый `pg_dump` (+ `chroma_db`/`obsidian_data` по флагу), хранить последние 14; `restore.sh` — восстановление с подтверждением.
- systemd: `secondbrain.service` (поднимает compose при загрузке) + таймер бэкапа (03:30) и, при выборе этого варианта, таймер `sync_tasks`; `install.sh` их ставит.
- `status.sh` — контейнеры, healthcheck, диск, последние ошибки, дата последнего бэкапа, время последней синхронизации задач.
- Перенос со старого ПК: скрипт/инструкция — текущая прод-БД (Postgres в Docker на Windows-ПК) → `pg_dump` → копирование → `restore.sh` → `export_tasks_to_note`. Старую БД не трогать.

## Round 4 — редактор заметок, ИИ-агент, провайдер Claude, API для Telegram-бота

Порядок частей: D → E → API.

### Часть D — редактирование заметок на сайте
D1. Режим «Редактировать» на странице заметки: Markdown-редактор (CodeMirror 6 или аналог, локально в `static/`) с подсветкой Markdown и frontmatter, предпросмотром (ПК — рядом, телефон — вкладки «Текст / Просмотр»), автодополнением `[[вики-ссылок]]` по названиям, Ctrl+S — сохранить, Esc — выйти. Удобно на 320 px и на ПК.
D2. Создание заметки: выбор папки (PARA) и шаблона из `99 - Templates` (Templater-код не исполнять; простые даты можно подставлять — решение в DECISIONS); frontmatter и строка «🔗 [[…MOC]]».
D3. Сохранение — через единый механизм записи (commit «notes: edit <путь> via site»). Обнаружение конфликтов: при открытии запомнить хэш файла; если при сохранении файл другой — не перезаписывать, показать дифф и варианты «Моя версия / Версия из хранилища / Скопировать мой текст». Черновик автосохраняется в браузере. Офлайн — очередь.
D4. Удаление и переименование — только с подтверждением в UI; при переименовании обновлять `[[ссылки]]` во всём хранилище одним коммитом, с предпросмотром списка затронутых файлов. Запрещено писать в `.obsidian/`, `.git/`, вне хранилища, не-.md файлы (кроме вложений — решение в DECISIONS).
D5. После сохранения — переиндексация в Chroma только изменённой заметки.
D6. Тесты: конфликт, повтор push, переименование с обновлением ссылок, опасные пути, XSS в предпросмотре, e2e «открыть → изменить → сохранить → видно в просмотре и в git тестового репо», responsive.

### Часть E — ИИ-агент, который редактирует заметки, + провайдер Claude
E1. **Провайдеры ИИ** за общей абстракцией: Gemini (цепочка фолбэков как есть), Ollama и новый **Claude (Anthropic API)**: `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` (по умолчанию `claude-haiku-5-5`, в Настройках можно выбрать `claude-sonnet-5-5`; ID сверить с docs.claude.com, записать в DECISIONS). Выбор провайдера и модели — в Настройках; без ключа Claude в списке недоступен. Обычный RAG-чат работает с любым провайдером.
E2. **Режим «Агент»** (переключатель у поля ввода; обычный чат остаётся). Инструменты (tool/function calling): `search_notes` (по названию + RAG), `read_note`, `list_folder`, `create_note`, `append_to_note`, `replace_in_note` (точная замена фрагмента, без перезаписи заметки целиком), `add_task` / `update_task` (через модуль задач). Инструмента удаления нет. Ограничения путей как в C3/D4.
E3. **Подтверждение:** агент не пишет сам — все изменения за ответ собираются в пакет, показываются как дифф по файлам с кнопками «Применить всё / Выбранное / Отклонить»; применение — один коммит через единый механизм записи («ai: <кратко запрос>»); кнопка «Откатить» (revert-коммит). Опция «Без подтверждения применять только добавления (append / новые заметки / новые задачи)» — по умолчанию выключена.
E4. **Правила хранилища в системном промпте агента** (frontmatter, разрешённые теги, вики-ссылки, привязка к MOC, callouts, чекбоксы, «меняй точечно»); источник — настраиваемая заметка (`VAULT_RULES_NOTE`) + встроенный дефолт. Содержимое заметок — данные, не инструкции (защита от prompt injection, тест).
E5. **Лимиты:** максимум 8 шагов инструментов на запрос, бюджет токенов, понятные сообщения; для агента на Gemini по умолчанию модель с большим дневным лимитом (Flash Lite) + фолбэк на 429; модели без tool calling — режим «Агент» недоступен с объяснением. Логи шагов агента (инструменты, файлы, токены) без содержимого заметок.
E6. **UI:** в ленте видно, что делает агент («Ищу… Читаю «…»… Готовлю изменения»), карточка диффа читаема на телефоне (переключатель «Изменения / Итоговый текст»), Markdown-рендер ответов.
E7. Тесты (все провайдеры замоканы): каждый инструмент, опасные пути, «без подтверждения не пишет», применение и откат, конфликт с параллельной правкой, лимит шагов, prompt injection, переключение провайдеров, e2e «попроси дописать заметку → дифф → применить → изменения в просмотре и в git».

### Часть API — REST API для Telegram-бота и других клиентов
Цель: Telegram-бот (отдельный проект владельца) работает только через API сайта и сам в git не пишет; сайт — единственный писатель в хранилище.
API1. Версионированный API `/api/v1/` с персональными токенами: создание/отзыв в Настройках (токен показывается один раз, в БД только хэш), права `read` / `write` / `ai`, срок действия (опционально), rate limit на токен, журнал вызовов (без содержимого заметок). Сессионные эндпоинты сайта и их CSRF-защита не затронуты.
API2. Эндпоинты: поиск заметок; чтение заметки; список папки; создание заметки (папка, шаблон, теги); дописать в заметку (в т.ч. «быстрый захват» во «Входящие» и в текущую недельную заметку — правило пути в DECISIONS); задачи (список с фильтрами, добавить, изменить статус/срок/приоритет, удалить) через модуль задач; вопрос к ИИ по заметкам (RAG, с выбором провайдера); агент: запрос → дифф + id пакета → отдельный вызов «применить»/«отклонить»; статус синхронизации. Все записи — через единый механизм записи с той же валидацией путей.
API3. Пользователь видит только своё хранилище; токен одного пользователя не даёт доступа к другому (тест).
API4. Документация `docs/API.md` на русском + OpenAPI-схема (`/api/v1/schema/`), примеры curl и пример минимального бота на Python (aiogram или python-telegram-bot): «/task текст» → задача, «/note текст» → быстрый захват, «/ask вопрос» → ответ ИИ, обычный текст → во «Входящие». Полноценного бота не писать — только пример в документации.
API5. Тесты: авторизация, права, отзыв и истечение токена, rate limit, изоляция пользователей, каждый эндпоинт (успех и ошибки), агентский поток через API, запись в тестовый git-репо.
API6. Деплой: API доступен через cloudflared; в `docs/DEPLOY.md` — как выдать токен боту и проверить API с сервера (`curl`).

## Round 5 — сайт как веб-версия хранилища, PWA, Obsidian в браузере, защита доступа

Цель раунда: с любого устройства и из любого места владелец открывает сайт и делает с заметками всё самое нужное — смотрит, ищет, редактирует, создаёт, спрашивает ИИ, работает с задачами и недельными планами. Полностью копировать Obsidian не нужно: для всего остального — настоящий Obsidian в браузере (F6).

### Часть F — веб-версия хранилища
F1. **Навигация:** дерево папок (PARA, эмодзи в названиях, сворачивание, запоминание состояния), быстрый переход Ctrl+K (fuzzy по названиям и alias'ам), полнотекстовый поиск с подсветкой и фильтрами (папка, тег, дата изменения), страница тегов, обратные ссылки и «упоминания без ссылки», локальный граф заметки и общий граф (лёгкая библиотека локально; на телефоне — упрощённый вид), недавние и избранные заметки.
F2. **Рендер как в Obsidian:** callouts (все типы, сворачиваемые `-`), чекбоксы со статусами `[ ] [x] [/] [>] [-]` — кликабельные, изменение сохраняется через единый механизм записи; встраивание `![[заметка]]`, `![[заметка#Раздел]]`, `![[картинка.png]]` (вложения из `99 - Cache`, с защитой путей и правильными заголовками контента); ссылки `[[Заметка#Раздел]]` и `[[Заметка|текст]]`; frontmatter как панель свойств; таблицы; математика (KaTeX локально); Mermaid. **Dataview-lite:** `LIST`, `TABLE`, `TASK` с `FROM` (папка/тег), `WHERE` (простые сравнения полей frontmatter, `file.name`, `file.mtime`, `completed`), `SORT`, `LIMIT` — выполняются на сервере, только чтение, с ограничением времени; неподдерживаемое показывается как код с пометкой «Откройте в Obsidian». Templater-код не исполнять. Тесты рендера на фикстуре-хранилище.
F3. **Недельные заметки:** кнопка «Эта неделя» — открыть или создать недельную заметку по `Template_Weekly` в правильной папке семестра с именованием как в существующих файлах (правило вывести из структуры, записать в DECISIONS; учебные недели, неделя A/B). Кнопка «Перенести незакрытые задачи из прошлой недели» — с предпросмотром диффа; в старой заметке задачи помечаются `[>]`. Календарь недель (аналог плагина Calendar).
F4. **PWA:** манифест, иконки, установка на телефон, service worker с офлайн-чтением недавно открытых заметок (только чтение; кэш очищается при выходе из аккаунта), плашка «Нет сети», быстрый захват (текст во «Входящие») с отправкой при появлении сети через офлайн-очередь.
F5. **Главная как «пульт»:** задачи на сегодня/неделю, текущая недельная заметка, недавние заметки, поле быстрого захвата, вход в ИИ-чат; красиво на телефоне и ПК.
F6. **Obsidian в браузере (полный функционал):** в прод-compose отдельный сервис `obsidian` на образе `lscr.io/linuxserver/obsidian` под отдельным профилем (по умолчанию выключен): volume конфигурации, хранилище через git (DOCKER_MODS `linuxserver/mods:universal-git` или отдельный клон + obsidian-git внутри), `restart: unless-stopped`, `shm_size`, без проброса портов наружу — доступ только через cloudflared на отдельном поддомене. В DEPLOY.md: как включить, первичная настройка хранилища и obsidian-git внутри, ресурсы, **предупреждение: в GUI контейнера sudo без пароля → только за Cloudflare Access**.
F7. **Защита доступа:** в DEPLOY.md пошагово — Cloudflare Access (одноразовый код на почту владельца) для сайта и поддомена Obsidian; `/api/v1/` исключён из Access (bypass по пути), защищён токенами. На сайте — 2FA (TOTP: подключение по QR, резервные коды, отключение с вводом кода), включаемая в Настройках; тесты.
F8. **Адаптивность и полировка:** все новые страницы на 11 размерах без переполнения, зоны нажатия ≥44 px, AA-контраст в обеих темах, клавиатурная навигация; скриншоты до/после в `docs/audit/round5/responsive/`.

### Сквозная проверка всей системы (главный критерий готовности Round 5)
Один большой e2e-тест (тестовый git-репо, все внешние API замоканы), который проходит путь владельца:
1) вход с 2FA → 2) «Эта неделя» создаёт недельную заметку → 3) быстрый захват через API с токеном «бота» → запись во «Входящие» → 4) задача через API → видна на сайте → 5) изменение задачи «в Obsidian» (прямой коммит во второй клон тестового репо) → видно на сайте после синхронизации → 6) правка заметки в редакторе → 7) ИИ-агент дописывает заметку → дифф → применить → откатить → 8) поиск, обратные ссылки и Dataview-lite показывают новые данные → 9) в истории git тестового репо все коммиты на месте, посторонний текст заметок не испорчен.
